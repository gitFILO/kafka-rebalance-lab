# 용량 산정서 예시

[용량 산정 절차](../docs/stage1-throughput/02-capacity-planning.md)를 가상 서비스에 적용한 예시다. 입력은 실제 서비스의 값이 아니다. 계수는 이 랩의 측정값이므로 결과는 운영 하드웨어에서 다시 재기 전까지 가설이다. 자기 서비스의 입력으로 다시 쓰면서 절차를 익힌다.

## 입력

| 항목 | 값 |
|---|---|
| 서비스 | 주문 이벤트 수집(가상) |
| 평균 유입 | 20,000건/s |
| 피크 배수 | 3 |
| 평균 레코드 | 1,000B |
| 보존 | 3일 |
| RF, `min.insync.replicas` | 3, 2 |
| 컨슈머 그룹 | 2개 |
| 압축 | lz4, 압축률 0.70 |
| 프로듀서 | `acks=all`, batch 64KB, linger 5ms |

## 계산

| 항목 | 식 | 결과 |
|---|---|---:|
| 평균 유입, 압축 전 | 20,000 × 1,012B | 20.2MB/s |
| 평균 유입, 압축 후 | 20.2 × 0.70 | 14.2MB/s |
| 피크 유입 | 14.2 × 3 | 42.5MB/s |
| 디스크 합계 | 14.2MB/s × 86,400 × 3일 × RF 3 | 11.0TB |
| 브로커당 디스크(4대) | 11.0TB ÷ 3 ÷ 0.7 | 5.3TB |
| 네트워크 입력 합계 | 42.5 × 3 | 128MB/s |
| 네트워크 출력 합계 | 42.5 × (2 + 2) | 170MB/s |
| 한 대 장애 시 브로커당 입력 | 128 ÷ 3 | 43MB/s |
| 한 대 장애 시 브로커당 출력 | 170 ÷ 3 | 57MB/s |
| 초당 요청 | 42.5MB/s ÷ 60KB | 708건 |
| 브로커 합계 CPU | 0.47 + 0.40ms × 708 + 6.9ms × 42.5 | 1.0코어 |

요청 크기 60KB는 측정값(124KB)의 절반이다. 측정은 부하가 높아 배치가 꽉 찬 경우이고, 이 서비스의 피크는 그보다 낮아 배치가 덜 찰 수 있어 보수적으로 잡았다.

## 결론

| 자원 | 산정 | 근거 |
|---|---|---|
| 브로커 수 | 4대 | RF 3에 복구 대상 1대를 더한 값. 디스크 외의 자원은 3대로도 충분하다 |
| 디스크 | 브로커당 6TB | 5.3TB에 여유를 더해 올림. 이 산정을 결정하는 자원이다 |
| 네트워크 | 10GbE | 1GbE(125MB/s)도 피크는 버티지만 복구 트래픽을 더하면 여유가 없다 |
| CPU | 측정 후 결정 | 랩 계수로 1.0코어(노트북 코어 기준, 컨슈머 몫 제외)다. 이 부하에서는 제약이 아니다 |

## 입력이 바뀌면

| 변경 | 영향 |
|---|---|
| 보존 7일 | 디스크 합계 25.7TB. 브로커 4대면 브로커당 12.2TB이므로 대수를 늘리는 쪽을 검토한다 |
| 압축을 zstd로(압축률 0.45) | 디스크 합계 7.1TB, 피크 유입 27MB/s. 프로듀서 CPU가 늘어난다 |
| 레코드를 키로 분산, 파티션 수 증가 | 배치가 덜 차서 초당 요청이 늘어난다. CPU 항을 다시 계산한다 |

## 측정하지 않은 것

- 컨슈머 fetch의 CPU와 지연
- 실제 디스크 I/O와 페이지 캐시(랩은 tmpfs)
- 실제 네트워크 왕복(랩은 같은 호스트)
- 토픽 `compression.type`이 프로듀서와 달라 재압축이 일어나는 경우
- 몇 시간 이상 지속되는 부하

운영 전에 [절차의 "운영 전 검증"](../docs/stage1-throughput/02-capacity-planning.md)을 수행해 계수를 바꾼다.
