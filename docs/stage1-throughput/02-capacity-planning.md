# Stage 1-02. 용량 산정

입력은 "초당 N건, 평균 S바이트, 보존 D일, RF R, 컨슈머 그룹 G개, 피크 배수 P"이고, 출력은 브로커 수와 브로커당 디스크, 네트워크, CPU다. 이 문서는 계산 절차와 이 랩에서 잰 계수를 정리한다. 가상 서비스로 끝까지 계산한 예시는 [results/capacity-plan.md](../../results/capacity-plan.md)에 있다.

절대값은 실제 하드웨어로 옮길 수 없다. 옮길 수 있는 것은 계산 구조와 계수를 재는 방법이다. 운영 환경에서는 같은 측정으로 계수만 바꿔 끼운다.

## 이 랩에서 잰 계수

| 계수 | 값 | 근거 | 운영으로 옮길 때 |
|---|---|---|---|
| 복제 배수 | 유입의 RF−1배 | 전체 측정에서 유입 113.47GB, 복제 유입 226.95GB(2.00배) | 그대로 쓴다 |
| 레코드 오버헤드 | 약 12B | `DefaultRecord`의 길이·속성·델타 필드와 배치 헤더(61B)의 레코드당 몫을 더한 계산값 | 그대로 쓴다 |
| 브로커 CPU(RF 3, 3대 합계) | 0.47코어 + 요청당 0.40ms + MB당 6.9ms | 13개 측정점 회귀, 오차 15% 이내 | 운영 하드웨어에서 다시 잰다 |
| 코어당 유입(RF 3, batch 64KB) | 50~104MB/s. 보수적으로 50MB/s | broker-cpu 묶음. 회차별로 두 배 갈린다 | 운영 하드웨어에서 다시 잰다 |
| 지연이 평평한 구간 | 포화의 약 75%까지 | load-steady 묶음(267MB/s, 포화 349MB/s) | 다시 잰다 |
| 압축률 | lz4 0.70, snappy 0.72, gzip 0.46, zstd 0.45 | 합성 JSON | 실제 페이로드로 다시 잰다 |
| 프로듀서 한 대의 한계 | 약 350MB/s(batch 64KB), 약 500MB/s(batch 256KB) | load, batch 묶음 | 앱의 처리 비용에 따라 달라진다 |

이 랩의 MB는 1,048,576바이트이고, 아래 계산의 MB는 1,000,000바이트다. 5% 차이는 CPU 모델의 오차보다 작아서 구분하지 않는다.

## 절차

### 1. 유입량

```text
평균 유입 = N × (S + 12B) × 압축률
피크 유입 = 평균 유입 × P
```

압축 후 바이트가 네트워크와 디스크를 지나므로 이후 계산은 모두 압축 후 값으로 한다. 피크 배수는 일별 최대가 아니라 분 단위 최대로 잡는다. 초 단위 버스트는 프로듀서 버퍼가 흡수한다.

### 2. 디스크

```text
디스크 합계 = 평균 유입 × 86,400 × D × R
브로커당 디스크 = 디스크 합계 ÷ (브로커 수 − 1) ÷ 0.7
```

보존 기간의 누적량은 피크가 아니라 평균이 정한다. 브로커 수에서 1을 빼는 이유는 한 대가 죽고 복제본을 다시 만든 뒤에도 남은 브로커가 사용률 상한 아래에 있어야 하기 때문이다. 상한 70%는 `BrokerDiskSpaceLow`(여유 25%)가 울리기 전에 멈추는 값이다. 디스크가 차면 브로커가 멈추므로([D07](../stage4-drills/D07-disk-full.md)) 다른 자원보다 여유를 넉넉히 둔다.

### 3. 네트워크

```text
브로커 합계 입력 = 피크 유입 × R
브로커 합계 출력 = 피크 유입 × (R − 1 + G)
브로커당 = 합계 ÷ (브로커 수 − 1)
```

입력은 프로듀서 1배와 복제 R−1배다. 출력은 복제 R−1배와 컨슈머 그룹 수만큼이다. 컨슈머는 압축된 채로 받으므로 압축 후 값으로 계산한다. 여기에 장애 복구 트래픽이 더해진다. 복구는 throttle로 제한하므로([D12](../stage4-drills/D12-replication-throttle.md)) 그 값만큼 여유를 남긴다.

### 4. CPU

```text
초당 요청 = 피크 유입 ÷ 요청 크기
브로커 합계 코어 = 0.47 + 0.40ms × 초당 요청 + 6.9ms × 피크 MB/s
```

요청 크기는 "브로커가 리더인 파티션 수 × 평균 배치 크기"이고 `max.request.size`가 상한이다. 운영 중이라면 프로듀서의 `records-per-request-avg`로 바로 알 수 있다. 요청 크기가 CPU를 크게 바꾸므로 평균 배치가 얼마나 차는지가 중요하다. 키가 있는 레코드는 모든 파티션에 흩어지므로 파티션이 많을수록 배치가 덜 찬다.

이 식에는 컨슈머 fetch 비용이 없고, 계수는 RF 3에서 쟀다. 컨슈머 몫은 Stage 1에서 재지 않았으므로 여유로 덮는다.

### 5. 브로커 수

세 자원에서 나온 대수 중 큰 값을 고른다. RF 3이면 최소 4대로 잡는다. 3대면 한 대가 죽었을 때 복제본을 다시 만들 곳이 없어 복구될 때까지 URP가 남는다.

### 6. 여유를 두는 이유

부하 곡선은 포화의 77%까지 평평했으니 그 근처까지 써도 될 것처럼 보인다. 그렇게 하면 안 되는 이유는 정지에서 회복하는 시간이다. 이용률 u에서 S초 멈추면 밀린 양을 되찾는 데 S × u/(1−u)초가 더 든다.

| 이용률 | 회복 시간(정지 시간의 배수) |
|---:|---:|
| 50% | 1배 |
| 70% | 2.3배 |
| 85% | 5.7배 |
| 95% | 19배 |

GC, 리더 이동, 컨슈머 리밸런스, 메트릭 수집처럼 정지를 만드는 사건은 운영에서 늘 일어난다. 이 랩에서도 포화의 87%부터 같은 목표가 실행마다 p99 22ms와 205ms로 갈렸다. 그래서 설계 상한은 측정한 포화의 70%로 둔다. 한 대가 죽어도 이 상한 안에 있어야 하므로 브로커 수 − 1로 계산한다.

### 7. 프로듀서 설정 점검

| 항목 | 판단 기준 |
|---|---|
| `batch.size` | 기본 16KB는 고부하에서 CPU를 많이 쓴다. 측정에서 64KB가 처리량 두 배였다. 메모리 비용은 파티션 수 × batch.size다 |
| `linger.ms` | 배치가 차는 시간보다 길게 잡아도 소용없다. 초당 유입과 batch.size로 계산한다 |
| `acks` | `all`을 기준으로 잡는다. 브로커 CPU는 비슷하지만 지연은 복제 왕복만큼 늘고, 연결 점유가 길어져 프로듀서 한 대의 최대 처리량이 측정에서 20% 낮았다 |
| 압축 | lz4가 처리량과 전송량의 균형이 좋았다. 앱 스레드가 압축을 하므로 gzip은 프로듀서 스레드 하나의 한계가 먼저 온다 |
| `buffer.memory` | 지연 상한이 된다. 버퍼 ÷ 처리량만큼 밀린 뒤에야 `send()`가 막힌다 |

### 8. 운영 전 검증

산정서의 값은 가설이다. 운영 하드웨어에서 다음을 재서 계수를 바꾼다.

1. `broker-cpu`와 같은 방식으로 브로커가 포화될 때까지 부하를 올려 코어당 유입을 잰다. 프로듀서를 여러 대 써서 프로듀서가 먼저 막히지 않게 한다.
2. 부하를 설계값으로 고정하고 몇 시간 돌린다. 이 랩의 측정은 2~15초이고 디스크가 메모리이므로 페이지 캐시와 디스크 I/O의 영향이 빠져 있다.
3. 수집 주기와 대상 메트릭을 운영 설정 그대로 둔 채 p99를 잰다. 측정에서 높은 부하일수록 수집의 영향이 커졌다.
4. 브로커 한 대를 내리고 같은 부하에서 지연과 복구 시간을 잰다.
