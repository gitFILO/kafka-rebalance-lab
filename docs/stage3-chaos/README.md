# Stage 3. 블라인드 장애 훈련(카오스)

## 목적

무엇이 언제 고장 날지 모르는 상태에서 장애를 감지하고, 원인을 확정하고, 조치한다. Stage 2에서는 장애 이름과 주입 시각을 알고 시작했다. 여기서는 둘 다 모르고, 장애는 2~3개가 연쇄로 이어지며, 장애가 아닌 정상 운영 사건(배포, 트래픽 변동)이 섞인다. 실무 장애 대응에서 시간이 드는 부분, 즉 "어느 신호가 원인이고 어느 신호가 결과인가"를 가려내는 능력을 기른다.

완료하면 다음을 할 수 있다.

- 여러 이상 신호 중 가장 먼저 시작된 것을 찾아 인과 사슬을 거꾸로 따라간다.
- 정상 운영 사건을 장애로 오인하지 않는다.
- 증상을 누르는 조치와 원인을 제거하는 조치를 구분하고, 해로운 조치를 피한다.
- 장애 보고서를 시간 지표(감지, 원인 확정)와 근거를 갖춰 작성한다.

## 개요

### 회차 구성

| 단계 | 내용 |
|---|---|
| 정상 상태 | 모든 회차가 같은 서비스 프로파일로 시작한다: consumer 프로토콜, 컨슈머 3대, 600 msg/s, 페이로드 200B, 프로듀서 `buffer.memory` 512KB. |
| 노이즈 | 회차마다 0~2개의 정상 운영 사건이 무작위 시점에 일어난다: 컨슈머 1대 재시작(배포), 컨슈머 1대 4초 정지(GC), 60초간 유입 20% 증가. |
| 주입 | 시작 후 30~150초 사이 무작위 시점에 카드 하나의 장애가 시작된다. 대상 브로커·파티션, 강도, 시차도 무작위다. |
| 대응 | 감지 → 범위 판단 → 원인 확정 → 조치 → 복구 확인 |
| 공개 | `chaos.sh reveal`이 정답, 실제 타임라인, 시간 지표, 채점 기준을 보여 준다. |

Grafana 어노테이션은 꺼진다. 대시보드에 주입 시각이 표시되지 않는다.

토픽 보존 기간은 10분이다(페이로드 200B에서 256MB 디스크를 지키는 값). 소비가 10분 넘게 멈추면 커밋되지 않은 데이터가 삭제되기 시작한다. 어느 카드든 대응이 늦으면 유실이 추가되므로 사실상의 대응 시간 제한이다.

### 카드 설계 기준

카드는 장애 하나의 정의다. 내장 카드는 5장이고, 두 유형만 허용한다.

| 유형 | 정의 | 허용하지 않는 것 |
|---|---|---|
| 인과 연쇄형 | 근본 원인 하나가 다음 장애를 부르고, 그것이 또 다음 장애를 부른다. 단계마다 Kafka의 실제 동작(설정, 코드 경로)이 연결 고리다. | 서로 무관한 장애를 같은 시각에 우연히 겹치기 |
| 운영 동시성형 | 각각은 정상인 운영 작업 두 개가 겹쳐 장애가 된다. 실무에서 일정이 겹치는 일은 흔하다. | 현실에서 동시에 일어날 수 없는 조합 |

모든 카드는 다음 조건을 지킨다.

- 각 단계가 메트릭이나 로그에 흔적을 남긴다. 근거 없이 추측해야만 맞힐 수 있는 카드는 없다.
- 클러스터 규모와 부하가 서로 모순되지 않는다(예: 브로커는 한가한데 컨슈머만 포화되는 식의 설정은 쓰지 않는다).
- 회차마다 대상과 강도가 바뀐다. 같은 카드를 다시 뽑아도 같은 답을 외워서 맞힐 수 없다.
- `chaos.sh validate Cx`로 인과 사슬의 각 단계가 실제로 재현되는지 판정한다.

### 봉인

시작할 때 카드, 매개변수, 정답, 타임라인을 `results/chaos/<id>/.sealed/`에 기록하고 정답의 SHA-256 앞 16자리(봉인 확인값)를 출력한다. `reveal`에서 같은 값이 나오면 회차 중에 정답이 바뀌지 않았다는 뜻이다.

### 재현 충실도

| 항목 | 실제 운영 | 이 랩 |
|---|---|---|
| 시간 축척 | 수 시간~수 일 | 보존 기간, poll 간격 등을 줄여 수 분 안에 진행 |
| 느린 브로커 | GC 정지, 디스크·네트워크 지연 | 컨테이너 주기적 정지(`docker pause`). Docker Desktop 커널에 tc qdisc가 없어 netem을 쓰지 못한다 |
| 관측 수단 | 메트릭, 로그, 트레이싱, 고객 문의 | 메트릭, 로그, Kafka CLI, 앱 이벤트 CSV |
| 노이즈 | 수십 개의 동시 사건 | 최대 2개 |
| 보존 기간 | 수 일 | 10분. 대응 지연이 곧 유실로 이어진다 |

## 진행 방식

### 규칙

사용해도 되는 것:

- Grafana, Prometheus(<http://localhost:9090>)
- Kafka CLI(`docker exec -e KAFKA_OPTS= broker-1 /opt/kafka/bin/...`)
- 컨테이너 로그(`docker logs`), 컨테이너 기동 여부(`docker ps`의 Up/Exited)
- run 디렉터리의 CSV(`events-*.csv`, `group.csv`, `lag.csv`)와 `scripts/analyze.py`
- 운영 조치: 브로커·컨슈머·프로듀서 재시작과 설정 변경, 토픽 설정 변경, 오프셋 리셋, 리더 선출, 증설

열지 않는 것(장애 주입 장치이거나 정답이다):

- `results/chaos/<id>/.sealed/`, `scripts/chaos/cards/`, `CHAOS_CARDS_DIR`
- run 디렉터리의 `control/`, `results/runs/.freeze-*`
- `docker inspect`, `docker events`, `docker ps`의 Paused 표시
- `chaos.sh validate`(정답이 출력된다)

### 회차 진행

```bash
./scripts/cluster.sh up            # 이미 떠 있으면 생략
./scripts/chaos.sh start           # 카드 무작위. 봉인 확인값을 적어 둔다
./scripts/chaos.sh report          # 보고서 파일 경로가 나온다. 지금 열어 둔다
```

1. **관찰:** 정상 상태의 대시보드 값을 먼저 기억한다(처리량, lag, 지연). 비교 기준이 없으면 이상을 판단할 수 없다.
2. **감지:** 이상을 확인한 시각을 보고서의 `- 감지 시각:` 줄에 `HH:MM:SS`로 적는다. 정상 운영 사건으로 판단한 것도 타임라인에 근거와 함께 적는다.
3. **범위 판단:** Stage 2의 진단 경로를 쓴다. 생산 경로인가 소비 경로인가, 전체인가 일부인가, 클러스터인가 클라이언트인가.
4. **원인 확정:** 가장 먼저 시작된 이상을 찾는다. 확정했으면 `- 원인 확정 시각:`을 적는다. 배제한 가설도 남긴다.
5. **조치:** 조치마다 시각, 이유, 결과를 적는다. 증상을 누르는 조치를 먼저 했다면 그 사실과 이유를 적는다.
6. **복구 확인:** 처리량, lag, 오류가 정상 상태로 돌아왔는지 본다. 유실·중복은 `python3 scripts/analyze.py gaps <run 디렉터리>`로 확인한다.
7. **공개와 채점:**

```bash
./scripts/chaos.sh reveal          # 정답, 타임라인, 시간 지표, 채점 기준
./scripts/chaos.sh stop            # 장애 흔적 정리, 워크로드 종료
```

8. [scoring.md](scoring.md) 기준으로 스스로 채점해 보고서 끝에 붙인다.

`chaos.sh status`는 경과 시간만 보여 준다. 회차 도중 그만두려면 `chaos.sh stop`.

### 특정 카드 다시 하기

```bash
./scripts/chaos.sh start C3
```

대상과 강도는 다시 무작위로 정해진다. 이미 정답을 본 카드라도 진단 순서와 시간을 줄이는 연습으로 쓴다.

### 비공개 카드

정답을 모르는 카드로 훈련하려면 다른 사람이 쓴 카드를 별도 디렉터리에 두고 지정한다.

```bash
CHAOS_CARDS_DIR=~/private-cards ./scripts/chaos.sh start
```

카드는 `Cx-<이름>.sh` 파일 하나이고, 다음 변수와 함수를 정의한다. 내장 카드를 예시로 쓴다.

| 항목 | 필수 | 내용 |
|---|---|---|
| `CARD_ID`, `CARD_TITLE`, `CARD_TYPE` | 예 | 식별자, 제목, 유형(인과 연쇄형·운영 동시성형) |
| `card_params` | 예 | 무작위 매개변수를 `KEY=VALUE` 줄로 출력한다. 봉인되고 이후 단계에서 환경 변수로 쓰인다 |
| `card_env` | 아니오 | 워크로드 시작 전 환경 변수(프로듀서·컨슈머 설정) |
| `card_inject` | 예 | 장애 주입. `chaos_event`로 타임라인을 남긴다. `scripts/lib-fault.sh` 함수를 쓴다 |
| `card_validate` | 예 | 인과 사슬 단계마다 `expect`로 PromQL 조건을 판정한다 |
| `card_teardown` | 아니오 | 정리 |
| `card_noise_ok` | 아니오 | 노이즈 종류(1 재시작, 2 정지, 3 유입 증가)를 받아 허용 여부를 반환한다. 정답과 구분이 불가능해지는 노이즈를 막는다 |
| `card_answer` | 예 | 정답 마크다운: 근본 원인, 인과 사슬, 핵심 신호, 올바른 조치, 해로운 조치 |

새 카드는 `chaos.sh validate Cx`가 PASS할 때까지 매개변수를 조정한다.

## 완료 기준

- 내장 카드 5장을 모두 한 번 이상 수행하고 보고서를 남겼다.
- 그중 3회 이상 [scoring.md](scoring.md) 기준 70점 이상을 받았다.
- 해로운 조치 감점이 없는 회차가 3회 이상이다.
- 비공개 카드를 1장 이상 직접 작성해 `validate`를 통과시켰다.
