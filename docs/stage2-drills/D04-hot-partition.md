# D04. 키 쏠림으로 인한 hot partition

## 목적

lag이 한 파티션에 몰리는 원인이 데이터(poison)인지 유입 분포(쏠림)인지 구분한다. 컨슈머 증설이 왜 효과가 없는지 파티션 단위 처리 모델로 설명하고, 파티션 증설이 왜 잘못된 조치인지 이해한다.

## 개요

| 항목 | 내용 |
|---|---|
| 상황 | 대형 고객 하나의 트래픽이 늘었고, 메시지 키가 고객 ID라 한 파티션으로 몰린다. |
| 주입 | 유입 900 msg/s, 그중 70%를 파티션 3으로(`producer.rate`, `producer.skew`) |
| 예상 증상 | 파티션 3의 lag이 증가한다. 그 파티션을 가진 멤버의 다른 파티션도 일부 밀린다. |
| 모범 조치 | 상류 키 분포를 고친다(쏠림 제거). |
| 소요 | 20분 |

## 진행 방식

```bash
./scripts/drill.sh start D04
```

1. Committed lag by partition에서 lag이 몰린 파티션을 찾는다.
2. Processed per partition에서 그 파티션의 처리량이 0인지, 상한에 붙어 있는지 본다. D03과 갈리는 지점이다.
3. Broker messages in과 브로커 쪽 파티션별 유입을 비교한다: `kafka_server_brokertopicmetrics_messagesin_total`에는 파티션 라벨이 없으므로 `lab_partition_logendoffset`의 증가율(`rate(lab_partition_logendoffset[1m])`)로 파티션별 유입을 구한다.
4. 증설을 시험한다: `./scripts/workload.sh scale 6`. 파티션 3의 lag이 줄어드는지 본다.
5. 원인을 제거한다(이 훈련에서는 상류 조치를 `drill.sh fix`로 대신한다). 
6. `drill.sh verify`, `drill.sh stop`.

확인할 것:

- 파티션 3의 유입률과 컨슈머 1대의 처리 상한을 수치로 비교했는가.
- 증설 후 파티션 3 소유 멤버가 가진 파티션 수와 처리량은 어떻게 바뀌었는가.
- 파티션을 24개로 늘리면 무엇이 바뀌고 무엇이 그대로인가.

---

## 해설

### 메커니즘

키가 있는 레코드는 `murmur2(key) % 파티션 수`로 파티션이 정해진다. 같은 키는 항상 같은 파티션으로 가고, 한 파티션은 그룹 안에서 한 멤버만 처리한다. 파티션 3의 유입(약 630 msg/s)이 컨슈머 1대의 처리 상한(약 400~500 msg/s)을 넘으면, 그룹 전체 처리량이 충분해도 파티션 3의 lag은 계속 늘어난다.

6대로 늘리면 파티션 3 소유 멤버의 다른 파티션이 다른 멤버로 옮겨 가므로 그 파티션들의 lag은 줄어든다. 파티션 3의 처리량은 그대로다.

### 진단 경로

| 단계 | 근거 | 판단 |
|---|---|---|
| 감지 | lag이 한 파티션에 집중 | poison(D03) 또는 쏠림 |
| 범위 | 그 파티션의 처리량이 0이 아니라 상한에 붙음 | 쏠림 |
| 원인 | 파티션별 유입률(`rate(lab_partition_logendoffset[1m])`)이 한 파티션만 높음 | 상류 키 분포 |
| 확인 | 증설 후에도 해당 파티션 lag 증가 지속 | 컨슈머 용량 문제가 아니다 |

### 조치 선택지

| 조치 | 효과 | 부작용·한계 |
|---|---|---|
| 키 salting(키에 접미사를 붙여 여러 파티션으로 분산) | 쏠림 해소 | 같은 고객 내 순서 보장이 깨진다. 컨슈머가 재조합해야 할 수 있다 |
| 대형 고객 전용 토픽 분리 | 격리 | 운영 대상 증가 |
| 해당 파티션 처리 비용 축소 | 상한 증가 | 근본 해결 아님 |
| 컨슈머 증설 | 해당 파티션에는 효과 없음 | 리밸런싱만 늘어난다 |
| 파티션 증설 | 해당 키는 여전히 한 파티션 | `murmur2 % N`의 N이 바뀌어 다른 키의 파티션 매핑이 바뀐다. 키 순서 보장이 증설 시점에 깨진다 |

### 코드 근거 (4.1.2)

- `BuiltInPartitioner.partitionForKey()`(`clients/.../producer/internals/BuiltInPartitioner.java:329`): `Utils.toPositive(Utils.murmur2(serializedKey)) % numPartitions`

### 재발 방지

- 알람: 파티션별 lag의 최대값/평균 비율(`max(lab_partition_lag) / avg(lab_partition_lag) > 5`)
- 설계: 키 카디널리티와 상위 키 비중을 측정해 토픽 설계 문서에 남긴다.

### 재현 충실도

이 훈련은 키 대신 파티션을 직접 지정해 쏠림을 만든다. 효과는 같다.
