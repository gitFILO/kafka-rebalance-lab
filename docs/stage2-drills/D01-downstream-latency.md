# D01. 다운스트림 지연으로 인한 lag 누적

## 목적

lag 증가를 보고 "처리량이 유입량보다 작다"는 사실과 그 원인(처리 시간 증가)을 구분해 확인한다. 증설로 해결되는 lag과 증설로 해결되지 않는 lag을 나누는 기준(파티션 수, 처리량 상한)을 계산으로 설명할 수 있게 한다.

## 개요

| 항목 | 내용 |
|---|---|
| 상황 | 컨슈머가 레코드마다 호출하는 저장소(DB, 외부 API)의 응답이 느려졌다. |
| 주입 | 전 멤버의 레코드당 처리 시간을 2ms → 8ms로 늘린다(`control/process_ms`). |
| 예상 증상 | 전 파티션 lag이 고르게 증가한다. 그룹은 Stable을 유지한다. |
| 모범 조치 | 컨슈머를 3대 → 6대로 증설한다. |
| 소요 | 15분 |

## 진행 방식

```bash
./scripts/drill.sh start D01
```

1. Overview의 Committed lag by partition이 모든 파티션에서 같이 오르는지, 일부만 오르는지 본다.
2. Consumer processed 합계와 Broker messages in을 비교한다. 차이가 lag 증가 속도다.
3. 그룹 상태, 멤버 수, 할당이 그대로인지 본다. 리밸런싱 문제인지 처리량 문제인지 가른다.
4. Clients에서 Poll idle ratio, Time between poll max를 본다. 컨슈머가 어디서 시간을 쓰는지 판단한다.
5. 조치를 정하고 실행한다. 증설하려면 `./scripts/workload.sh scale <n>`을 쓴다.
6. `./scripts/drill.sh verify`로 lag이 500 아래로 내려오는지 확인하고 `drill.sh stop`.

확인할 것:

- 증설 전에 몇 대가 필요한지 계산했는가. 계산식과 실제 회복 시간을 비교한다.
- 컨슈머를 13대 이상으로 늘리면 어떻게 되는가.
- lag이 다 빠질 때까지 걸린 시간은 무엇으로 결정되는가.

---

## 해설

### 메커니즘

컨슈머 1대의 처리량 상한은 대략 `1000 / process_ms` msg/s다. 8ms면 대당 125 msg/s, 3대 합계 375 msg/s로 유입 600 msg/s보다 작다. lag은 초당 약 225건씩 쌓인다. 처리 루프가 poll 간격 안에 끝나므로(100건 × 8ms = 0.8초) 리밸런싱은 일어나지 않는다. 그룹 상태만 보면 정상으로 보이는 이유다.

6대로 늘리면 750 msg/s가 되어 초당 150건씩 줄어든다. 회복 시간은 `누적 lag / (처리량 - 유입량)`이다.

### 진단 경로

| 단계 | 근거 | 판단 |
|---|---|---|
| 감지 | Overview: Committed lag 전 파티션 증가 | 특정 파티션 문제가 아니다(D03, D04와 구분) |
| 범위 | Consumer processed 합계 < Broker messages in, 멤버별 처리량이 비슷하게 감소 | 모든 멤버가 같이 느려졌다 |
| 원인 | Clients: Poll idle ratio가 0에 가까움, Time between poll은 30초보다 작음 | 처리 시간이 늘었다. poll 간격 초과(D02)는 아니다 |
| 확인 | Process delay setting 패널(실무에서는 다운스트림 응답 시간 메트릭) | 원인 확정 |

### 조치 선택지

| 조치 | 효과 | 부작용·한계 |
|---|---|---|
| 컨슈머 증설 | 처리량이 대수에 비례해 증가 | 파티션 수(12)가 상한. 증설 순간 리밸런싱으로 짧은 정지. 다운스트림 부하가 더 커져 지연이 악화될 수 있다 |
| 다운스트림 복구 | 근본 해결 | 컨슈머 쪽에서 통제할 수 없는 경우가 많다 |
| 배치 처리(여러 레코드를 한 번에 저장) | 레코드당 비용 감소 | 코드 변경 필요 |
| 파티션 증설 | 컨슈머 상한을 늘림 | 키 순서가 바뀐다. 이미 쌓인 lag은 기존 파티션에 남는다 |

### 코드 근거 (4.1.2)

- 서버 할당자 `UniformHomogeneousAssignmentBuilder`(`group-coordinator/.../assignor/UniformHomogeneousAssignmentBuilder.java`): 파티션을 멤버 수로 나눠 균등 배분한다. 멤버가 파티션보다 많으면 남는 멤버는 파티션을 받지 못한다.

### 재발 방지

- 알람: `deriv(lab_group_totallag[5m]) > 0`이 10분 지속(실무에서는 consumer lag exporter의 그룹 lag). lag 절댓값보다 증가 추세가 먼저 알려 준다.
- 용량 기준: 컨슈머 대당 처리량 실측값과 최대 유입량으로 필요 대수를 문서화한다. 파티션 수가 그 대수보다 커야 한다.

### 재현 충실도

실무의 다운스트림 지연은 시간에 따라 변하고, 증설하면 다운스트림 부하가 늘어 더 느려지는 되먹임이 있다. 이 훈련의 지연은 고정값이라 증설 효과가 그대로 나타난다.
